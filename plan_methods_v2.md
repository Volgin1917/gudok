## 0. Ключевая сверка с текущим кодом (важно!)

В рекомендациях исходной точкой названы шесть полей паспорта «гипотеза, формула, источник,
порог, публикация, первый расчёт». **Это поля паспорта метрик из `plans.py`** (реестр
метрик-кандидатов на странице «Планы»). Фактический паспорт методики в `methods.py` v1.1
устроен иначе — шесть строк: **Вход, Выход, Метрики качества, Модуль платформы,
Неопределённость, Порядок проверки на платформе** (+ `code`, `group`, `status`, `mod`, `n`,
`ideo`, `id`, `name`, `ess`). Строка «метрика или методика добавляется только через паспорт —
с гипотезой, формулой, источником данных, порогом тревоги…» на странице — это цитата правила
для **метрик** «Инфопространства», а не шаблон паспорта методики. Отсюда главный открытый
вопрос реформы: **унифицировать ли два шаблона** (см. §2.1, решение Р1).

Что уже есть на странице (не нужно делать заново):

| Рекомендация | Где уже реализовано |
|---|---|
| Якоря карточек | `id="m01"…"m41"` (без дефиса!), ссылки из IDEO_TABLE, dossier, elections |
| Бейдж группы в карточке | `.mgrp` (краткое имя группы) + `.mgrp-ideo` |
| Сворачиваемость карточек | нативный `<details>`, работает без JS; `toggle`-обработчик меняет «паспорт ↓/↑» |
| Фильтры по группе и статусу | чипы `#fGroup`/`#fStatus` + счётчик «показано N из 41» |
| Цветовые токены | `--paper/--ink/--accent(#D63F1F)/--muted/--rule/--pos/--neu/--neg`, светлая+тёмная тема |

  убрать атрибут (summary и так кнопка) либо синхронизировать в toggle-обработчике. → п. 9.2 ✔️→🔧

## Часть I. Реестр методик

### 1. Структура

**1.1 Трёхуровневая иерархия** — ✅ принято.
- `methods.py`: новый реестр `SUBGROUPS = {group_key: [(sub_key, title), …]}` + поле `sub`
  у каждого паспорта. Проект подгрупп (уточняется редакцией):
  - сбор: «Каналы сбора», «Качество сбора», «Реестры источников»;
  - текст: «Классификация», «Тональность», «Сюжеты и кластеры», «Извлечение сущностей»;
  - динамика: «Каскады», «Сетевые метрики», «Латентность»;
  - проверка: «Верификация», «Антонимы/противодействие», «Журнал»;
  - экономика: «Собственность», «Госзакупки», «Труд»;
  - аудитория: «Поведение», «Вовлечение»;
  - контекст: «Исторические ряды», «Сравнения»;
  - представление: «Визуализация», «Публикация»;
  - выборы: «Явка и мобилизация», «Аномалии протоколов», «География», «Сравнение циклов».
- Рендер: секция на группу (`<section id="g-sbor">`) → внутри подгруппы (заголовок-линейка
  `.h3rule`) → карточки. Группа сворачивается целиком (`<details class="mgroup" open>` —
  нативно, без JS).
- Сортировка внутри группы: статус (work → test → queue), затем код. `sorted_by_code()`
  остаётся для стенда; добавляется `sorted_by_status()`.
- Тесты: подгруппа из известного списка, покрытие (каждая методика имеет `sub`, подгруппы
  не пустуют), порядок сортировки.

**1.2 Префиксная нумерация (S-/T-/N-/I-)** — ⚠️ решение Р2.
Коды `М-XX` зашиты в ссылках: `dossier.py` (конвейер карточки), `elections` (М-37…М-41),
`plans.py` (конвейер внедрения), `IDEO_TABLE`, якоря `#m01…#m41`, тексты ROADMAP/README,
журнал М-28. Перенумерация = ломка всех ссылок + потеря преемственности журнала.
**Рекомендация: компромисс из самой рекомендации** — коды `М-XX`保留, поле `group` уже есть,
вывести его явной колонкой в сводной таблице (в конце страницы) и бейджем в карточке (уже есть).
Префиксы групп при этом видны в навигации («Сбор · 6»).

**1.3 Сводная таблица внизу + sticky-полоса** — ✅ принято (комбинация, как предложено).
- Внизу страницы — **полная таблица всех 41 методики**: код (ссылка-якорь), название, группа,
  подгруппа, статус, модуль, блок «что блокирует» (см. 3.2), выборка n.

### 4. Содержание паспортов

Зависит от решения **Р1** (шаблон). Варианты:

- **Р1-A «единый метрический шаблон»**: все 41 паспорт переводим на поля
  гипотеза/формула/источник/порог/публикация/первый расчёт + новые поля §2.1. Плюсы: один
  контракт со шкалой «Планов». Минусы: для процедурных методик (М-01 мониторинг, М-28 журнал,
  протоколы верификации) «гипотеза» и «порог тревоги» искусственны — получится имитация
  фальсифицируемости, что противоречит духу п. 4.1.
- **Р1-B «два типа паспортов» (рекомендуется)**: ядро общее (вход/выход/метрики качества/модуль/
  неопределённость/порядок проверки — текущие 6) + тип `kind: metric|procedure`:
  - `metric` получает обязательные **гипотеза** (фальсифицируемая), **формула** (с расшифровкой
    переменных, моноширинный блок), **порог тревоги** (значение + обоснование + реакция);
  - `procedure` получает обязательные **правило** (формальная формулировка процедуры),
    **критерий корректности**;
  - общим: **источник данных** (файл/URL + период + частота), **ограничения**, **пример**.
  Валидация (2.2) различает требования по `kind`. Метрики «Инфопространства» из `plans.py`
  при этом остаются в своём реестре — но получают перекрёстные ссылки `related` на методики.
- **Р1-C «текущие 6 + дополнения»**: ничего не переименовываем, добавляем только поля §2.1
  (включая ограничения и пример); гипотезы/формулы не вводим. Минимальная ломка тестов и
  контента, но рекомендация 4.1–4.2 (фальсифицируемость) остаётся не закрытой.

Независимо от варианта:
